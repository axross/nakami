# Routing and Data

Apply this reference when adding or changing a route, touching the on-device database, or writing a query or mutation.

## Screens and Routes

The Expo app development capability owns the routing layer itself — file notation, navigators, thin route modules. What follows has no owner there and is stated here instead: every data-backed screen renders before its data arrives, and the fallback needs the same test hook the loaded screen has, or an e2e flow cannot assert the state it is actually looking at.

**Guidelines:**

- MUST give each data-backed screen a loading state that renders without the loaded data, propagating the screen's `testID` convention to the fallback so e2e flows can assert it.
- MUST keep the root error boundary (the error-reporter wrap in `src/app/_layout.tsx`) intact; a route needing custom error UI adds its own boundary beneath it.
- SHOULD give unmatched routes a friendly `+not-found.tsx` screen once the app has more than one route (tracked as issue #8).

## Deep Links

Every route is reachable through the `nakami://` deep-link scheme, declared as `app.json` → `scheme`. That makes route and search parameters an external input surface rather than an internal one: they arrive from outside the app, from a sender it cannot vouch for.

**Guidelines:**

- MUST treat every parameter arriving through a deep link as untrusted input, validated before use — see the Zod validation and deep-link confirmation rules in [runtime-conventions.md](./runtime-conventions.md).

## Data Layer

Tables are defined in one place and migrations are generated from them, never written by hand. One detail is load-bearing and easy to miss: Drizzle's expo-sqlite migrator (`useMigrations`) is **not** wired into the app yet, so a generated migration would never actually run — the change that lands the first migration has to wire it.

**Guidelines:**

- MUST define tables in `src/core/db/schema.ts` and commit the migration generated by `npm run db-migrate:generate` alongside the schema change.
- MUST NOT hand-edit or amend a file under `src/core/db/migrations/` — they are generated. Change the schema and generate a new migration instead.
- MUST reach the database only through the shared client in `src/core/db/client.ts`; feature-level access (queries/mutations wrapping that client) stays in the owning feature.
- MUST wire Drizzle's expo-sqlite migrator (`useMigrations`) into `src/app/_layout.tsx` as part of the change that lands the first migration.
- MUST give every data-layer read an explicit projection, filter, and result limit where the dataset can grow, and MUST NOT iterate a list re-fetching each related record.

## Server State

The TanStack Query capability owns the option-factory pattern in full, and this codebase already follows it: `get<Name>QueryOptions` / `get<Name>MutationOptions` factories under each feature's `queries/` and `mutations/`, consumed directly with `useQuery()` / `useMutation()`.

Query keys are the one place this codebase and the installed capability disagree. The two existing keys in `src/collections/queries/collection-list-query.ts` and `collection-records-query.ts` put tenancy in a trailing filter object — `["collections", scope]` — which the capability marks as a Major finding; migrating them is tracked as issue #67. New code does not follow them.

**Guidelines:**

- MUST use the shared `queryClient` from `src/core/helpers/query-client.ts`; there is exactly one.
- MUST read the Zustand store through `useAuthStore.getState()` **inside** the `queryFn`/`mutationFn`, never in the factory body.
- MUST give a new query the tenancy-rooted key form (`["users", userId, "collections", …]`), not the trailing-filter form the two existing keys use.
